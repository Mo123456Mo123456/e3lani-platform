# معمارية إعلاني

## حدود الأنظمة

- `apps/mobile`: واجهة المستهلك والمعلن. لا تحفظ صلاحيات أو حالات دفع أو حالة إعلان محليًا.
- `apps/web`: صفحات عامة قابلة للفهرسة وتجربة تصفح الإعلانات.
- `apps/admin`: واجهة داخلية؛ كل إجراء فيها يعاد التحقق من دوره داخل NestJS.
- `services/api`: المصدر الوحيد لحقيقة الحسابات والمحتوى والأسعار والدفع والإشراف.
- `services/media-worker`: يستهلك طابور `media-processing` ولا يقبل طلبات عامة.
- `packages/database`: نموذج Prisma والترحيلات وبيانات catalog/pricing الابتدائية.

## تدفق الإعلان المجاني

1. يطلب التطبيق رابط رفع مؤقتًا من API.
2. يرفع الملف مباشرة إلى S3 ثم يطلب finalize.
3. يتحقق API من الحجم والنوع المعلنين ويضيف مهمة BullMQ.
4. يتحقق العامل من magic bytes ويضغط الصور أو يحول الفيديو ويولد thumbnail.
5. لا يقبل إنشاء الإعلان إلا media بحالة `READY` ومملوكة للمستخدم.
6. في `FREE_LAUNCH` ينشأ الإعلان `ACTIVE` مباشرة بمدة مأخوذة من `PricingItem`.
7. لا توجد مراجعة بشرية قبل النشر؛ يبدأ تدخل الإدارة من بلاغ أو اعتراض.

## فصل المحتوى

`Ad` و`ProfilePost` نموذجان منفصلان مع جداول وسائط وحفظ منفصلة. استعلامات `/ads` لا
تحتوي أي join أو union مع المنشورات. `/profiles/:slug` هو المكان العام الوحيد الذي يعيد
المنشورات المنشورة.

## الدفع

`PaymentAdapter` له تطبيقان: `DisabledPaymentAdapter` و`MoyasarPaymentAdapter`.
الافتراضي disabled ويرفض إنشاء checkout. عند التفعيل ينشأ الطلب من أسعار قاعدة البيانات،
ويظل الإعلان `AWAITING_PAYMENT` حتى webhook صحيح التوقيع. لا تعتمد المنصة على redirect
العميل كإثبات دفع.

## الأمان

- OTP مجزأ بـ HMAC، محدود المحاولات والمدة، ويستهلك مرة واحدة.
- access token قصير وrefresh token عشوائي مخزن كـ SHA-256 مع تدوير.
- كل طلب إداري يمر عبر JWT ثم `RolesGuard`.
- قرارات الإيقاف والأدوار والأسعار تكتب في `AuditLog`.
- روابط الإعلان تقبل الهاتف أو HTTPS/HTTP فقط حسب النوع.
- روابط رفع S3 قصيرة المدة، ويعاد فحص object metadata ثم magic bytes.
- rate limiting عالمي، ومجموعة أشد لمسارات المصادقة قابلة للتوسعة.

## التوسع

خدمات API والعامل stateless ويمكن زيادة نسخها. PostgreSQL هو المصدر المركزي، Redis
للطوابير، وS3 للوسائط. يفضل إضافة CDN أمام bucket عام أو signed delivery domain، وتشغيل
تجميع `AnalyticsEvent` إلى `AdMetricDaily` كمهمة دورية عند نمو حجم الأحداث.
