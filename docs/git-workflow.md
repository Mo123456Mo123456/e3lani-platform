# سير Git واعتماد GitHub مصدرًا للحقيقة

## المبدأ

المستودع الخاص [`Mo123456Mo123456/e3lani-platform`][1] هو المصدر الرسمي الوحيد للشفرة. تُنفذ جميع التغييرات على فروع Git وتصل إلى `develop` أو `main` عبر Pull Requests. لا تمثل نسخة ZIP أو مجلد Manus المحلي مصدرًا موازيًا للحقيقة، ولا يجوز أن يحتوي المستودع بيانات تشغيلية للمستخدمين.

## الرسم التشغيلي

```text
feature/* أو fix/*
        │
        ▼
 Pull Request + CI
        │
        ▼
     develop
        │  Release PR + clean-clone verification
        ▼
       main ─── tag / GitHub Release
```

## خطوات العمل

| الخطوة | الإجراء |
|---|---|
| 1 | `git switch develop && git pull --ff-only` |
| 2 | إنشاء `feature/<name>` أو `fix/<name>` من `develop` |
| 3 | Commits صغيرة بصيغة Conventional Commits مع اختبارات ملازمة |
| 4 | دفع الفرع وإنشاء Pull Request إلى `develop` |
| 5 | انتظار نجاح TypeScript وESLint وVitest وبناء الخادم وتصدير الويب |
| 6 | دمج Squash أو Rebase وفق وضوح التاريخ، ثم حذف الفرع البعيد |
| 7 | عند الإصدار، Pull Request من `develop` إلى `main` والتحقق من استنساخ نظيف |
| 8 | إنشاء Tag موقع منطقيًا وإصدار GitHub مع ملخص `CHANGELOG.md` |

## حماية الفروع

يجب منع الدفع المباشر والحذف وForce Push على `main` و`develop`، واشتراط Pull Request وفحص CI ناجح ومحادثات محلولة. يبقى `main` مستقرًا فقط. إن لم تسمح خطة GitHub الحالية بتطبيق قواعد الحماية على مستودع خاص، توثق القيود ويستمر الالتزام الإجرائي حتى تفعيل الميزة.

## المهاجرات والخدمات

تُحفظ ملفات Drizzle في Git، لكن تنفيذها يتم على بيئات منفصلة مع نسخة احتياطية وخطة تراجع. قاعدة البيانات والتخزين السحابي ومزود OAuth والدفع ليست أجزاء من GitHub. يجب ألا تعتمد اختبارات Pull Request على بيانات إنتاج أو مفاتيح إنتاج.

## التراجع

يمكن التراجع عن تغيير تطبيقي عبر Revert Commit أو إصدار تصحيحي. أما مهاجرات قاعدة البيانات فتحتاج مهاجرة عكسية مراجعة أو استعادة مدروسة؛ لا تُستخدم أوامر Git لإرجاع بيانات قاعدة البيانات.
