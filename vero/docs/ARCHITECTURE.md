# VERO — معمارية النظام

> **VERO — كل زيارة لها إثبات.**
> نظام مستقل (Single-Tenant / Self-Hosted) لإثبات تنفيذ خدمات النظافة عبر QR + GPS.

---

## 1. المبدأ المعماري

| المبدأ | القرار |
|---|---|
| نموذج التسليم | نسخة مستقلة لكل شركة. لا Multi-Tenant، لا License Server، لا حساب مركزي للبائع. |
| الاستضافة | Self-Hosted على سيرفر الشركة عبر Docker Compose. |
| قاعدة البيانات | PostgreSQL 16 + PostGIS 3 محلية داخل نفس الـstack. |
| الاتصال الخارجي | لا يوجد أي اتصال إجباري بخدمة خارجية. الخرائط الافتراضية OpenStreetMap/MapLibre. |
| مصدر الحقيقة | قاعدة البيانات فقط. لا LocalStorage كقاعدة رئيسية، لا بيانات وهمية. |
| فشل الـBackend | يظهر خطأ صريح في الواجهات. لا يوجد Demo Fallback إطلاقًا. |

## 2. الطبقات داخل الـBackend

```
src/
  config/      قراءة متغيرات البيئة والتحقق منها (fail-fast)
  db/          Pool + مُهاجر SQL (migrations/*.sql) + مساعدات الاستعلام
  core/        أدوات مشتركة: أخطاء، تجزئة كلمات المرور، JWT، توقيع QR، الجغرافيا، المعرفات
  modules/     كل وحدة = service.ts (منطق) + routes.ts (HTTP) + schema.ts (Zod)
  http/        بناء السيرفر، المصادقة، RBAC، Rate Limit، OpenAPI، معالجة الأخطاء
```

**قاعدة صارمة:** كل قرار أمني (RBAC، الملكية، صلاحية الرمز، النطاق الجغرافي) يُنفَّذ في `service`/`http` على الخادم. الواجهة تخفي الأزرار فقط كتحسين بصري، ولا يُعتمد عليها أبدًا.

## 3. تدفق إثبات الزيارة (Proof Chain)

```
العامل يمسح QR
  │
  ├─ 1. فك رمز QR:  vero1.<binPublicId>.<nonce>.<hmacSHA256>
  ├─ 2. التحقق من التوقيع بمفتاح QR_SIGNING_KEY (ثابت لكل نسخة)
  ├─ 3. جلب الحاوية + التحقق أنها فعّالة وتخص نفس الشركة
  ├─ 4. التحقق من ربط الجهاز (device binding) وأن العامل نشط
  ├─ 5. حساب المسافة بين GPS المسح وموقع الحاوية (PostGIS ST_Distance geography)
  ├─ 6. تقييم الاحتيال (دقة GPS، السرعة اللحظية، بُعد المسار، تكرار الجهاز)
  ├─ 7. تحديد الحالة: VERIFIED | SUSPICIOUS | INVALID
  ├─ 8. منع التكرار: زيارة واحدة معتمدة لكل حاوية في اليوم (service_day)
  ├─ 9. حفظ scan + proof_hash (سلسلة تجزئة مرتبطة بالسجل السابق)
  └─ 10. تحديث لوحة الإدارة (استعلام مباشر من قاعدة البيانات)
```

### تفاصيل الحالات

| الحالة | الشرط |
|---|---|
| `VERIFIED` | التوقيع صالح + الجهاز مرتبط + المسافة ≤ نطاق الحاوية + لا إشارات احتيال حاسمة |
| `SUSPICIOUS` | التوقيع صالح لكن المسافة خارج النطاق، أو إشارة احتيال (قفزة GPS، دقة سيئة جدًا، تعارض مع مسار السيارة) |
| `INVALID` | توقيع غير صالح، رمز غير معروف، حاوية معطّلة، جهاز غير مرتبط أو موقوف |

**سلسلة الإثبات:** لكل مسح `proof_hash = SHA256(prev_hash ‖ bin ‖ token ‖ lat ‖ lon ‖ ts ‖ worker ‖ vehicle ‖ device)`.
تعديل أي سجل قديم يكسر السلسلة، ويُكشف عبر `GET /v1/scans/chain/verify`.

## 4. منع التكرار اليومي

- لكل مسح يُحسب `service_day` بتوقيت الشركة (`COMPANY_TIMEZONE`، افتراضيًا `Asia/Riyadh`).
- فهرس فريد جزئي: `UNIQUE (bin_id, service_day) WHERE status = 'VERIFIED' AND counted = true`.
- المسح المكرر لا يُرفض من المستخدم؛ يُحفظ في `scan_attempts` مع `duplicate_of` ويُعلَّم `counted = false`.
- عند بداية يوم جديد تعود كل الحاويات تلقائيًا إلى «لم تتم خدمتها» لأن الحساب يعتمد على `service_day` وليس على عمود حالة قابل للتلف.

---

## 5. وضع عدم الاتصال (Offline)

1. التطبيق يخزّن كل مسح محليًا في SQLite مع `client_uuid` (UUID v4 يولّده الجهاز).
2. تُرسل الدفعات إلى `POST /v1/sync/scans` عند عودة الاتصال.
3. الخادم يطبّق **Idempotency** على `client_uuid` (فهرس فريد)، فإعادة الإرسال لا تُنشئ سجلًا مكررًا.
4. الرد يعيد لكل عنصر: `accepted | duplicate | rejected` + السبب، ليحذف الجهاز ما نجح فقط.
5. نقاط المسار تُرسل بنفس الآلية عبر `POST /v1/sync/route-points`.

## 6. الأمن

| البند | التنفيذ |
|---|---|
| كلمات المرور | `scrypt` (N=16384, r=8, p=1) + ملح 16 بايت لكل مستخدم |
| الجلسات | JWT موقّع HS256 بمفتاح `JWT_SECRET`، صلاحية قصيرة + Refresh |
| رموز QR | HMAC-SHA256 بمفتاح `QR_SIGNING_KEY` — لا يمكن تزوير رمز حاوية |
| أجهزة العمال | `device_token` عشوائي 32 بايت يُخزَّن **مجزَّأً** (SHA-256) في قاعدة البيانات |
| RBAC | تحقق على مستوى كل مسار في الخادم (`requireRole`) |
| المدخلات | Zod على كل Body/Query/Params |
| SQL Injection | استعلامات مُعاملة (parameterized) حصريًا عبر `pg` |
| Rate Limit | عام + حدّ أشد على `/auth/login` و`/devices/activate` |
| الأسرار | متغيرات بيئة فقط. لا مفاتيح داخل الواجهات. |
| سجل التدقيق | `audit_logs` لكل عملية حساسة مع `before`/`after` |

## 7. تدفق تفعيل جهاز العامل

```
الإدارة → إنشاء كود تفعيل لعامل + سيارة
        → يظهر ككود من 8 خانات + QR
العامل  → يفتح VERO ويمسح كود التفعيل مرة واحدة
الخادم  → يتحقق من الكود (صالح، غير مستهلك، غير منتهٍ)
        → ينشئ device + device_binding (company, worker, vehicle)
        → يعيد device_token (يُعرض مرة واحدة فقط)
التطبيق → يخزّن الرمز في SecureStore ويفتح مباشرة على شاشة التشغيل
```

## 9. ما لا يفعله النظام (بصراحة)

- لا يتتبّع العامل خارج جلسة العمل.
- لا يضمن استحالة التزوير المطلق: يمكن نظريًا تصوير الملصق. لذلك يوجد GPS + مسار السيارة + ربط الجهاز + كشف القفزات — وهذه تجعل التزوير مكلفًا وقابلًا للكشف، لا مستحيلًا.
- لا يعمل GPS بدقة داخل المباني المغلقة؛ لذلك النطاق قابل للضبط لكل حاوية.
